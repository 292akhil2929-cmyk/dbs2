Problem Statement

What we built

ShopSphere is a full-stack e-commerce platform for tech and lifestyle products targeting UAE consumers. Customers browse products, add them to a persistent cart, apply discount coupons, and place orders. Admins manage inventory, view analytics, and run promotions. The project demonstrates a production-grade relational database alongside a modern React frontend.

Why this domain

E-commerce is the canonical domain for relational databases because it naturally exercises every concept in CS F212:

  • Entity modelling — products, users, orders are distinct real-world entities
  • Relationships — orders contain many items, users have many addresses, categories can have sub-categories (self-referencing FK)
  • Normalization — a naive single-table design violates 1NF (multiple images per product), 2NF (address depends on user not order), and BCNF (brand info creates a transitive dependency through product)
  • Transactions — placing an order must atomically deduct stock, record items, create a payment record, and clear the cart — partial failure must rollback everything
  • Triggers — stock deducted automatically on order insert, restored on cancellation, ratings recalculated on review changes
  • Analytics — views and procedures provide revenue reports, customer lifetime value, low-stock alerts without repeated joins in application code

End-to-end Order Flow

  1. User clicks "Add to Cart" → React state update (no DB call yet)
  2. User opens cart, clicks "Place Order"
  3. Frontend fetch POST /api/orders with items + total
  4. Railway API starts a transaction, inserts into ORDERS
  5. For each cart item: INSERT INTO ORDER_ITEMS
  6. Trigger 1 (trg_check_stock_before_order) fires — validates stock; SIGNAL if insufficient → transaction rolls back
  7. Trigger 2 (trg_deduct_stock_after_order) fires — decrements stock_qty
  8. Trigger 7 (trg_increment_coupon_usage) fires — increments used_count
  9. Trigger 10 (trg_audit_product_update) fires — logs stock change to AUDIT_LOG
  10. Trigger 13 fires — records status in ORDER_STATUS_HISTORY + sends notification
  11. COMMIT → response 200 → frontend shows "Order Placed!"

If street/city/country were in ORDERS, they'd depend on the user, not the order — a partial dependency. Extracting to ADDRESSES resolves this. Users can also reuse addresses across multiple orders.

Purpose: Brand entity extracted from PRODUCTS to eliminate transitive dependency and achieve BCNF.

BCNF Justification

Without BRANDS: product_id → brand_name → {country, website} — transitive dependency. With BRANDS: brand_id → {name, country, website} and product_id → brand_id only. No transitive dep.

Table 6 — PRODUCT_IMAGES

1NF Justification

A product has multiple images. Columns img1_url, img2_url, img3_url would violate 1NF (repeating groups). One row per image — fully atomic.

Key columns: is_primary TINYINT(1) — the main display image. Views and JOINs use WHERE pi.is_primary = 1 to get exactly one image per product.

Table 7 — PRODUCT_ATTRIBUTES (EAV)

Purpose: Flexible product specifications using the Entity-Attribute-Value pattern.

Why EAV

A smartphone has RAM, Storage, OS. A racket has string tension, grip size, shaft flex. These can't be fixed columns — different categories have completely different specs. EAV uses one row per attribute: (product_id, attr_name, attr_value).

Example data for iPhone 15 Pro: (Storage: 256GB), (RAM: 8GB), (Display: 6.1 inch Super Retina XDR), (OS: iOS 17)

Table 9 — ORDERS

Master order record. Key columns:

  • status ENUM — pending → confirmed → processing → shipped → delivered / cancelled / refunded

Table 10 — ORDER_ITEMS

Price Snapshot Design

unit_price stores the price at time of order. If we derived it from PRODUCTS.price, the order history would change when prices update. Storing it is intentional and correct — it also removes the transitive dependency item_id → product_id → current_price.

UNIQUE KEY uq_order_product(order_id, product_id) — prevents the same product appearing twice in one order.

Table 11 — PAYMENTS

1:1 with ORDERS via UNIQUE KEY on order_id. Supports 7 payment methods: credit_card, debit_card, paypal, bank_transfer, cash_on_delivery, apple_pay, google_pay. gateway_resp TEXT stores raw JSON from payment gateway for dispute resolution.

Table 12 — REVIEWS

Verified purchase reviews. order_id FK ensures only actual buyers can review — cannot insert a review without a real order. UNIQUE(user_id, product_id) — one review per user per product. Rating triggers (4/5/6) keep PRODUCTS.avg_rating auto-updated.

Table 13 — CART_ITEMS

Persistent cart stored in DB (not localStorage). UNIQUE(user_id, product_id) prevents duplicate cart entries. CASCADE DELETE on both user and product FKs.

Table 14 — WISHLISTS

Saved items. Trigger 14 uses this table to send restock notifications — when a wishlisted product comes back in stock (0 → >0), all users who saved it get an in-app notification.

Table 15 — AUDIT_LOG

Immutable audit trail. Written by triggers — never by application code. No FKs on changed_by or record_id — intentional. If a user or product is deleted, the audit record must survive. Stores old/new values as JSON columns for full before/after state.

Table 16 — NOTIFICATIONS

In-app notification feed. Written by Trigger 13 (order status changes), Trigger 14 (restock alerts), and sp_broadcast_promo (marketing). idx_notif_unread(user_id, is_read) composite index optimises the very common "get unread count" query.

Table 17 — SHIPPING_ZONES

Per-emirate rates used by fn_zone_shipping_fee. 7 UAE zones: Dubai (AED 10/25, free >500), Abu Dhabi (15/30, free >500), Sharjah (15/30), Ajman (20/35), RAK (20/40), Fujairah (25/45, free >1000), UAQ (20/40).

Table 18 — TAGS

Product labels: Bestseller (#F59E0B amber), New Arrival (#10B981 green), Limited (#EF4444 red), Eco Friendly (#22C55E), Staff Pick (#3B82F6 blue), Clearance (#6B7280 gray), Bundle Deal (#8B5CF6 purple). color_hex CHAR(7) stores CSS hex for UI badges.

Table 19 — PRODUCT_TAGS (Junction)

1NF Justification

Without this table, tags would need to be a multi-valued column in PRODUCTS (e.g. "Bestseller,Staff Pick") violating 1NF. The junction table gives each tag assignment its own row. Composite PK (product_id, tag_id) prevents duplicate assignments.

Table 20 — ORDER_STATUS_HISTORY

Full audit of every order status transition — required for SLA tracking and dispute resolution. Written by Trigger 13 automatically on every ORDERS.status change. Seed data shows Order #1 going through: pending → confirmed → processing → shipped → delivered with comments at each step.

Normalization Analysis

The naive e-commerce "god table" would look like:

OrderLine(order_id, user_name, user_email, street, city, product_name,
          brand_name, brand_country, category_name, tag1, tag2, tag3,
          quantity, price)

This violates 1NF (multi-valued tags), 2NF (address depends on user not order), and BCNF (brand_country transitively depends on brand_name). We fix each level:

Functional Dependencies — Explicit Notation

-- USERS
user_id → {email, password_hash, full_name, phone, role, is_active, created_at}
email → {user_id} -- email is candidate key (UNIQUE)

-- CATEGORIES
category_id → {name, parent_id, description, icon_url, is_active}
name → {category_id} -- name is candidate key (UNIQUE)

-- BRANDS
brand_id → {name, country, website, logo_url, is_active}
name → {brand_id} -- name is candidate key (UNIQUE)

-- PRODUCTS
product_id → {category_id, brand_id, name, slug, description, price, compare_price, stock_qty, sku, weight_kg, avg_rating, review_count, is_active, is_featured}
slug → {product_id} -- slug is candidate key (UNIQUE)
sku → {product_id} -- sku is candidate key (UNIQUE)

-- ORDERS
order_id → {user_id, address_id, coupon_id, subtotal, discount_amt, shipping_fee, tax_amt, total_amount, status, ordered_at}

-- ORDER_ITEMS (composite key)
(order_id, product_id) → {quantity, unit_price}
-- unit_price is NOT derived from product_id alone — it is the price AT ORDER TIME (snapshot)

-- COUPONS
coupon_id → {code, type, discount_value, min_order_amt, max_discount, expires_at, max_uses, used_count}
code → {coupon_id} -- code is candidate key (UNIQUE)

-- PRODUCT_ATTRIBUTES (composite key)
(product_id, attr_name) → {attr_value}

-- PRODUCT_TAGS (pure junction — all attributes are key)
(product_id, tag_id) → {tagged_at}

First Normal Form (1NF)

Requirement: Every attribute must be atomic — no repeating groups, no multi-valued attributes.

ViolationFix Applied
Product has multiple images → columns img1, img2, img3 in PRODUCTSPRODUCT_IMAGES table — one row per image
Product has multiple tags → comma string in single columnPRODUCT_TAGS junction table
Product specs vary by category (RAM, string_tension, etc.)PRODUCT_ATTRIBUTES EAV table
User has multiple addressesADDRESSES table — one row per address

Second Normal Form (2NF)

Requirement: In 1NF + every non-key attribute fully depends on the entire primary key (relevant for composite PKs).

Violation Example

If ORDER_ITEMS had (order_id, product_id, quantity, unit_price, user_street, user_city):
• user_street depends on order_id, not on product_id → partial dependency
Fix: Address is in ADDRESSES, referenced by ORDERS via address_id FK, not in ORDER_ITEMS at all.

Our composite-key tables are all in 2NF:

  • (order_id, product_id) → quantity — quantity depends on both (which product in which order)
  • (order_id, product_id) → unit_price — price snapshot depends on both
  • (product_id, attr_name) → attr_value — value depends on which attribute of which product

Third Normal Form (3NF)

Requirement: In 2NF + no transitive dependencies (non-key attribute must not depend on another non-key attribute).

Violation — Brand in PRODUCTS

product_id → brand_name → {brand_country, brand_website}
brand_country only reachable through brand_name → transitive!
Fix: BRANDS table. Now: product_id → brand_id and brand_id → {name, country, website}

Similarly: product_id → category_name → description was transitive → CATEGORIES table extracted.

Boyce-Codd Normal Form (BCNF)

Requirement: For every non-trivial FD X → Y, X must be a superkey.

In our PRODUCTS table, all determinants (product_id, slug, sku) are superkeys ✓
In USERS, determinants (user_id, email) are both superkeys ✓
In BRANDS, determinants (brand_id, name) are both superkeys ✓

Had we left brand details in PRODUCTS, brand_name would be a determinant that is NOT a superkey of PRODUCTS → BCNF violation. Extracting BRANDS resolves this.

Summary Table

Design ChoiceNormal FormWhat it fixes
PRODUCT_IMAGES separate1NFMulti-valued images attribute
PRODUCT_TAGS junction1NFMulti-valued M:N tags
PRODUCT_ATTRIBUTES EAV1NFVariable specs per category

Views (7)

Views are stored SELECT statements treated as virtual tables. They simplify complex queries and provide a stable interface over the underlying tables.

VIEW 1vw_product_catalog

Purpose: Complete product listing with brand, parent category, and primary image — 4-table JOIN pre-built as a view.

SELECT p.*,
  ROUND(((compare_price - price) / compare_price) * 100) AS discount_pct,
  c.name AS category_name,
  pc.name AS parent_category,    -- self-join for parent
  b.name AS brand_name,
  pi.url AS primary_image
FROM PRODUCTS p
JOIN  CATEGORIES c  ON p.category_id = c.category_id
LEFT JOIN CATEGORIES pc ON c.parent_id = pc.category_id  -- double join same table
LEFT JOIN BRANDS b  ON p.brand_id = b.brand_id            -- LEFT: books have no brand
LEFT JOIN PRODUCT_IMAGES pi ON pi.product_id = p.product_id AND pi.is_primary = 1;

The double CATEGORIES join handles hierarchy: c = direct category (Smartphones), pc = parent (Electronics).

VIEW 2vw_order_summary

Purpose: Admin order dashboard — customer name, address, item count, payment status in one query. CONCAT(street, ', ', city, ', ', country) builds a readable address. COUNT(oi.item_id) counts line items per order.

VIEW 3vw_revenue_by_category

Purpose: Revenue breakdown per category. Uses SUM(oi.quantity * oi.unit_price) with unit_price (price snapshot) for historical accuracy. Excludes cancelled/refunded orders.

VIEW 4vw_low_stock

Purpose: Inventory alert — products with ≤10 units. WHERE stock_qty <= 10 AND is_active = 1 ORDER BY stock_qty ASC. Used by sp_dashboard_stats.

VIEW 5vw_customer_ltv

Purpose: Customer Lifetime Value. LEFT JOIN ORDERS so customers with no orders appear with LTV=0. COALESCE(SUM(total_amount), 0) handles NULL from empty LEFT JOIN. Only counts non-cancelled/refunded orders.

VIEW 6vw_product_tags

Purpose: Products with tags as concatenated string. Uses MySQL's GROUP_CONCAT(t.name ORDER BY t.name SEPARATOR ', ') to aggregate multiple tag rows into "Bestseller, Staff Pick" — presentational; underlying data remains normalised in PRODUCT_TAGS.

VIEW 7vw_unread_notifications

Purpose: Unread notification count per user. SUM(CASE WHEN is_read = 0 THEN 1 ELSE 0 END) counts only unread rows — more efficient than two separate subqueries.

Stored Functions (7)

Functions return a single value and can be called inside SELECT/WHERE clauses. They are either DETERMINISTIC (same input → same output, no DB reads) or READS SQL DATA.

FUNCTION 1fn_apply_coupon

Signature: fn_apply_coupon(subtotal, type, discount_val, max_discount) → DECIMAL

IF type = 'percentage' THEN
  disc = ROUND(subtotal * discount_val / 100, 2)
  IF max_discount IS NOT NULL AND disc > max_discount THEN
    disc = max_discount   -- cap at max (FLASH50 capped at AED 2000)
  END IF
ELSE
  disc = discount_val     -- fixed amount
END IF
IF disc > subtotal THEN disc = subtotal  -- can't discount more than cart value
RETURN disc

Example: fn_apply_coupon(2000, 'percentage', 50, 800) → 50% of 2000 = 1000, capped at 800 → returns 800

FUNCTION 2fn_discounted_price

Generic % discount helper. Handles edge cases: NULL price → NULL, pct ≤ 0 → original price, pct ≥ 100 → 0.00. Formula: ROUND(price * (1 - pct/100), 2)

FUNCTION 3fn_cart_subtotal

SELECT COALESCE(SUM(ci.quantity * p.price), 0) FROM CART_ITEMS ci JOIN PRODUCTS p ... — calculates total cart value. COALESCE(..., 0) returns 0 for empty carts. Called by sp_place_order.

FUNCTION 4fn_validate_coupon

All-in-one validation: checks code exists + is_active + not expired + under max_uses + subtotal ≥ min_order_amt. Returns discount amount or 0 if invalid. Can be used directly in SELECT: SELECT fn_validate_coupon('FLASH50', 1500)

FUNCTION 5fn_customer_order_count

SELECT COUNT(*) FROM ORDERS WHERE user_id = p AND status NOT IN ('cancelled','refunded') — counts completed orders. Can drive loyalty tier logic.

FUNCTION 6fn_shipping_fee

FUNCTION 7afn_zone_shipping_fee

FUNCTION 7bfn_price_with_vat

Triggers (14)

Triggers execute automatically when INSERT/UPDATE/DELETE occurs on a table. They enforce business rules at the DB level regardless of which application makes the change.

TRIGGER 1 BEFORE INSERT trg_check_stock_before_order on ORDER_ITEMS 
SELECT stock_qty INTO v_stock FROM PRODUCTS WHERE product_id = NEW.product_id;
IF v_stock < NEW.quantity THEN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Insufficient stock';
END IF

BEFORE — check happens before insert so we can abort cleanly. SIGNAL SQLSTATE '45000' = user-defined exception, aborts statement and triggers ROLLBACK.

TRIGGER 2 AFTER INSERT trg_deduct_stock_after_order

UPDATE PRODUCTS SET stock_qty = stock_qty - NEW.quantity WHERE product_id = NEW.product_id — fires after insert is committed. Trigger 1 already confirmed stock is sufficient.

TRIGGER 3 AFTER UPDATE trg_restore_stock_on_cancel on ORDERS

Guard: NEW.status = 'cancelled' AND OLD.status NOT IN ('cancelled','refunded') prevents double-restoring. Multi-table UPDATE with JOIN restores all products in one statement. Also writes to AUDIT_LOG.

TRIGGERS 4/5/6 AFTER INSERT/UPDATE/DELETE trg_update_rating_on_* on REVIEWS

Keep avg_rating and review_count in PRODUCTS auto-maintained. Trigger 6 uses COALESCE(..., 0) for when last review is deleted (AVG of empty set = NULL).

TRIGGER 7 AFTER INSERT trg_increment_coupon_usage on ORDERS

IF NEW.coupon_id IS NOT NULL THEN UPDATE COUPONS SET used_count = used_count + 1 — tracks redemption count for max_uses enforcement.

TRIGGER 8 BEFORE INSERT trg_auto_slug_on_insert on PRODUCTS

Auto-generates slug from name: LOWER(REPLACE(REPLACE(name, ' ', '-'), '/', '-')). BEFORE trigger can modify NEW.slug. "iPhone 15 Pro" → "iphone-15-pro".

TRIGGERS 9/10 AFTER INSERT/UPDATE trg_audit_product_* on PRODUCTS

Write to AUDIT_LOG using JSON_OBJECT('name', name, 'price', price, 'stock', stock). Trigger 10 only fires if price or stock changed: IF OLD.price != NEW.price OR OLD.stock_qty != NEW.stock_qty.

TRIGGER 11 BEFORE INSERT trg_single_default_address on ADDRESSES

If new address is is_default=1 and user already has a default: silently set new address to is_default=0. Cannot UPDATE existing default in the same trigger (MySQL restriction — prevents recursive loops). BEFORE trigger can modify NEW.column.

TRIGGER 12 AFTER INSERT trg_audit_user_register on USERS

Logs every new user registration: JSON_OBJECT('email', email, 'role', role) into AUDIT_LOG.

TRIGGER 13 AFTER UPDATE trg_order_status_history on ORDERS

When OLD.status <> NEW.status: (1) INSERT into ORDER_STATUS_HISTORY, (2) INSERT into NOTIFICATIONS for the customer. Two INSERTs, one trigger, one transaction.

TRIGGER 14 AFTER UPDATE trg_notify_restock on PRODUCTS

When OLD.stock_qty = 0 AND NEW.stock_qty > 0: INSERT notifications for all wishlist users via INSERT...SELECT from WISHLISTS. One product restock can trigger thousands of notifications in a single set-based operation.

Stored Procedures (9)

PROCEDURE 1sp_place_order

The most complex object in the schema — full checkout in a transaction with 12 steps:

sp_place_order(user_id, address_id, coupon_code, pay_method, ship_method,
               OUT order_id, OUT message)

1. Validate cart not empty (COUNT CART_ITEMS)
2. Validate address belongs to user (security check)
3. Resolve coupon (check active + not expired + under max_uses)
4. fn_cart_subtotal(user_id) → subtotal
5. Validate minimum order for coupon
6. fn_apply_coupon(...) → discount
7. SUM(qty * weight_kg) → total weight
8. fn_shipping_fee(weight) → shipping (×2 for Express)
9. (subtotal - discount) × 0.05 → VAT
10. subtotal - discount + shipping + vat → total

START TRANSACTION
  INSERT INTO ORDERS
  CURSOR LOOP: FETCH each cart item → INSERT ORDER_ITEMS
               (Triggers 1+2 fire per INSERT)
  INSERT INTO PAYMENTS
  DELETE FROM CART_ITEMS
COMMIT

CURSOR: Iterates cart items row-by-row. Needed because stock-check trigger fires per INSERT, not as a set operation.

EXIT HANDLER FOR SQLEXCEPTION: Catches any SQL error (including Trigger 1's SIGNAL) → ROLLBACK + set order_id=-1 + RESIGNAL.

PROCEDURE 2sp_dashboard_stats

Returns 10 KPI metrics in one SELECT: total_customers, total_orders, total_revenue, active_products, pending_orders, low_stock_count, total_reviews, avg_order_value, items_in_carts, revenue_last_30d. Each is a correlated subquery evaluated in one pass.

PROCEDURE 3sp_top_selling_products(p_limit)

Complex Queries

Q1 — Correlated Subquery: Products Above Category Average Price

A correlated subquery references the outer query's columns. It executes once per outer row.

SELECT p.product_id, p.name, p.price, c.name AS category,
  (SELECT ROUND(AVG(p2.price),2) FROM PRODUCTS p2
   WHERE p2.category_id = p.category_id) AS cat_avg   -- correlated!
FROM PRODUCTS p JOIN CATEGORIES c ON p.category_id = c.category_id
WHERE p.price > (
  SELECT AVG(p3.price) FROM PRODUCTS p3
  WHERE p3.category_id = p.category_id  -- runs once per outer row
)

For each product, MySQL runs the inner SELECT with that product's category_id. In Smartphones (avg ~AED 4166): iPhone 15 Pro (4999) and Samsung S24 Ultra (4499) are above average; OnePlus 12 (2999) is below.

Q2 — Nested Subquery: Customers Who Spent Above Average

SELECT u.full_name, u.email, SUM(o.total_amount) AS total_spent
FROM USERS u JOIN ORDERS o ON u.user_id = o.user_id
WHERE o.status = 'delivered'
GROUP BY u.user_id
HAVING SUM(o.total_amount) > (
  SELECT AVG(s.tot) FROM (        -- level 2
    SELECT SUM(total_amount) AS tot
    FROM ORDERS WHERE status = 'delivered'
    GROUP BY user_id              -- level 1 (derived table)
  ) s
);

Three levels: innermost = total per customer, middle = average of those totals, outer = customers above that average.

Q3 — Window Function: Rank Products by Revenue Within Category

SELECT product_name, category_name, revenue,
  RANK() OVER (PARTITION BY category_name ORDER BY revenue DESC) AS cat_rank
FROM vw_revenue_by_category;

PARTITION BY resets rank for each category. RANK() gives ties the same rank and skips next numbers (1,1,3). DENSE_RANK() would give 1,1,2. ROW_NUMBER() would give 1,2,3 regardless of ties.

Q4 — EXISTS / NOT EXISTS: Buyers Who Never Reviewed

SELECT u.user_id, u.full_name FROM USERS u
WHERE EXISTS (SELECT 1 FROM ORDERS o WHERE o.user_id = u.user_id)
  AND NOT EXISTS (SELECT 1 FROM REVIEWS r WHERE r.user_id = u.user_id);

EXISTS stops scanning on first match (short-circuit). SELECT 1 is conventional — column doesn't matter, only row existence. Finds customers to target for review-request emails.

Q5 — Multi-Level Join: Full Order Breakdown

SELECT o.order_id, u.full_name, b.name AS brand, p.name AS product,
  oi.quantity, oi.unit_price, (oi.quantity * oi.unit_price) AS line_total
FROM ORDERS o
JOIN USERS u       ON o.user_id    = u.user_id
JOIN ORDER_ITEMS oi ON o.order_id  = oi.order_id
JOIN PRODUCTS p    ON oi.product_id = p.product_id
LEFT JOIN BRANDS b ON p.brand_id   = b.brand_id  -- LEFT: books have no brand
ORDER BY o.order_id;

5-table chain. LEFT JOIN on BRANDS preserves products without brands (books with brand_id = NULL).

Q8 — Function Call in SELECT: Shipping Zone Rates

SELECT sz.zone_name, sz.emirate,
  fn_zone_shipping_fee(sz.emirate, 0) AS std_fee,    -- calls function
  fn_zone_shipping_fee(sz.emirate, 1) AS express_fee,
  sz.free_above
FROM SHIPPING_ZONES sz WHERE sz.is_active = 1 ORDER BY sz.base_fee;

Demonstrates calling a stored function inline in a SELECT.

Quick-Reference Cheat Sheet

Likely professor questions with model answers.

How many tables and what's the overall structure?
20 tables. Core entities: USERS, PRODUCTS, ORDERS, ORDER_ITEMS, PAYMENTS. Supporting normalisation: CATEGORIES (self-ref hierarchy), BRANDS (extracted for BCNF), ADDRESSES (extracted for 2NF), PRODUCT_IMAGES/ATTRIBUTES/TAGS (1NF). Operational: CART_ITEMS, WISHLISTS, REVIEWS, COUPONS. System: AUDIT_LOG, NOTIFICATIONS, ORDER_STATUS_HISTORY, SHIPPING_ZONES, TAGS, PRODUCT_TAGS.
Why is BRANDS a separate table?
BCNF. Without it: product_id → brand_name → brand_country (transitive dependency — brand_name is not a superkey of PRODUCTS). With BRANDS: brand_id → {name, country, website} and product_id → brand_id only. Every non-trivial FD now has a superkey as determinant.
Why does ORDER_ITEMS store unit_price?
Price snapshot. Product prices change over time. If we derived price from PRODUCTS.price, order history would show wrong amounts after price updates. Storing unit_price at order time ensures historical accuracy. It also removes the transitive dependency item_id → product_id → current_price.
What does the cursor in sp_place_order do?
A cursor iterates over the user's cart items row-by-row and inserts each as an ORDER_ITEMS row. This is necessary because Trigger 1 (stock check) fires per INSERT — we need per-row processing. CURSOR → OPEN → LOOP: FETCH INTO vars → INSERT ORDER_ITEMS (trigger fires here) → END LOOP → CLOSE.
What happens if stock runs out mid-order?
Trigger 1 (BEFORE INSERT on ORDER_ITEMS) fires for each item. If stock < requested quantity, it calls SIGNAL SQLSTATE '45000'. This raises a user-defined exception. The EXIT HANDLER in sp_place_order catches it, calls ROLLBACK (undoes all INSERTs so far), sets order_id=-1, and RESIGNALs the error to the API caller.
How does avg_rating stay up to date without a cron job?
Three AFTER triggers on REVIEWS: Trigger 4 (INSERT), Trigger 5 (UPDATE), Trigger 6 (DELETE). Each runs SELECT AVG(rating) and SELECT COUNT(*) on REVIEWS for that product and UPDATEs the PRODUCTS row. Trigger 6 uses COALESCE to return 0 when the last review is deleted (AVG of empty set = NULL).
What is the EAV pattern and why use it?
Entity-Attribute-Value. PRODUCT_ATTRIBUTES stores flexible specs as rows: (product_id=1, attr_name='RAM', attr_value='8GB'). Used because different product categories have completely different specs — a smartphone has RAM/Storage/OS, a racket has weight/grip/string_tension. Adding 50+ nullable columns to PRODUCTS for all possible specs would be impractical.
Explain SIGNAL SQLSTATE '45000'
MySQL's mechanism to raise a user-defined exception from inside a trigger or stored procedure. SQLSTATE '45000' = "unhandled user-defined exception". It aborts the current statement, propagates up through the call stack, and if inside a transaction will trigger a ROLLBACK unless caught by a DECLARE EXIT HANDLER FOR SQLEXCEPTION.
Why does AUDIT_LOG have no foreign keys?
Intentional. An audit log must be immutable and permanent. If AUDIT_LOG.record_id had a FK to PRODUCTS, deleting a product would either cascade-delete its audit records (destroying the trail) or block deletion (data management problem). No FKs means the log is append-only and survives any table changes.
What normalization form is the schema in?
BCNF. 1NF: no multi-valued attributes (PRODUCT_IMAGES, PRODUCT_TAGS, PRODUCT_ATTRIBUTES tables). 2NF: addresses separated from orders (removed partial dependency). 3NF/BCNF: brands and categories extracted from products (removed transitive dependencies). Every non-trivial FD has a superkey as determinant.
How does the frontend work without a server?
Next.js output:"export" generates a fully static site (HTML+CSS+JS). All data fetching is client-side via fetch() in useEffect hooks. The Railway backend is optional — if offline, the catch block in the useEffect silently keeps MOCK_PRODUCTS. The "Offline · Mock data" / "Live · Railway DB" badge shows which source is active.
What is the self-referencing FK in CATEGORIES?
parent_id FK → category_id in the same CATEGORIES table. NULL = top-level category. Electronics (id=1, parent=NULL) → Smartphones (id=6, parent=1). ON DELETE SET NULL means if Electronics is deleted, Smartphones becomes top-level rather than being deleted or orphaned.
Explain the correlated subquery (Q1)
A correlated subquery references a column from the outer query. In Q1, the inner SELECT AVG(price) has WHERE p3.category_id = p.category_id — p.category_id comes from the outer row. MySQL re-runs the subquery for every outer row, using that row's category_id. This finds products priced above their category's average.
What are the 7 coupon codes?
WELCOME10 (10%, any order, max AED 500), SUMMER20 (20%, min AED 200, max AED 800), FLASH50 (50%, min AED 1000, max AED 2000), VIP30 (30%, min AED 500, max AED 1500), STUDENT15 (15%, min AED 100, max AED 300), FLAT100 (AED 100 off, min AED 500), TECH500 (AED 500 off, min AED 5000).
How does Trigger 14 (restock notifications) work?
AFTER UPDATE on PRODUCTS. Guard: OLD.stock_qty = 0 AND NEW.stock_qty > 0 (product just restocked). Then INSERT...SELECT: inserts one notification row per row in WISHLISTS for that product_id. This is a set-based operation — one trigger execution could insert hundreds of notifications. Called implicitly by sp_restock_product.
