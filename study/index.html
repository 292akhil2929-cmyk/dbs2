All 20 Tables — With GitHub Links

Every table with its GitHub line range in schema.sql, purpose, and key design decisions.

Table 1 — CATEGORIES
schema.sql L19–L33

Self-referencing FK: parent_id → category_id same table. NULL = top level. Electronics(1) → Smartphones(6). ON DELETE SET NULL keeps children as top-level if parent deleted.

15 categories: Electronics, Fashion, Home & Kitchen, Books, Sports, + 10 sub-categories

Table 2 — USERS
schema.sql L38–L52

email VARCHAR(191) not 255 — utf8mb4 InnoDB index limit is 767 bytes; 191×4=764 fits. Role ENUM enforces 'customer'/'admin'/'vendor' at DB level. password_hash = bcrypt.

Table 3 — ADDRESSES
schema.sql L57–L72

Extracted from USERS for 2NF. Address depends on user, not order. One user → many addresses. Default enforced by Trigger 11.

Table 4 — BRANDS
schema.sql L77–L86

Extracted from PRODUCTS for BCNF. Without this: product_id → brand_name → country is transitive. 15 brands: Apple, Samsung, Sony, Nike, Levi's, IKEA, Dell, JBL, Lenovo, DJI…

Table 5 — PRODUCTS ⭐
schema.sql L91–L123

Central table. DECIMAL(10,2) for price (not FLOAT). FULLTEXT index on (name, description) for search. avg_rating/review_count cached (maintained by Triggers 4/5/6). CHECK constraints on price≥0, stock≥0, rating 0-5.

Table 6 — PRODUCT_IMAGES
schema.sql L128–L139

1NF fix — multiple images can't be columns (img1, img2, img3). One row per image. is_primary=1 used in JOINs to get main display image.

Table 7 — PRODUCT_ATTRIBUTES
schema.sql L144–L154

EAV pattern — (product_id, attr_name, attr_value). iPhone → (RAM:8GB, Storage:256GB, OS:iOS17). Different product types need different specs — can't be fixed columns.

Table 8 — COUPONS
schema.sql L159–L177

type ENUM('percentage','fixed'). max_discount caps % coupons. used_count auto-incremented by Trigger 7. 7 codes: WELCOME10, SUMMER20, FLASH50, VIP30, STUDENT15, FLAT100, TECH500.

Table 9 — ORDERS ⭐
schema.sql L182–L206

Stores subtotal, discount_amt, shipping_fee, tax_amt, total_amount separately for transparent billing. Status ENUM: pending→confirmed→processing→shipped→delivered/cancelled/refunded.

Table 10 — ORDER_ITEMS ⭐
schema.sql L211–L223

unit_price = price snapshot at order time. Not derived from PRODUCTS.price — that changes. UNIQUE(order_id, product_id) prevents duplicates.

Table 11 — PAYMENTS
schema.sql L228–L245

1:1 with ORDERS via UNIQUE on order_id. 7 methods: credit_card, debit_card, paypal, bank_transfer, cash_on_delivery, apple_pay, google_pay. gateway_resp TEXT stores raw JSON.

Table 12 — REVIEWS
schema.sql L250–L269

order_id FK ensures only buyers review. UNIQUE(user_id, product_id) = one review per product. rating CHECK 1-5. Triggers 4/5/6 auto-update PRODUCTS.avg_rating on any review change.

Table 13 — CART_ITEMS
schema.sql L274–L286

Persistent DB cart (survives browser close). UNIQUE(user_id, product_id). Cleared by sp_place_order after checkout.

Table 14 — WISHLISTS
schema.sql L291–L301

Saved items. Trigger 14 queries this table when a product is restocked (stock 0→>0) to send notifications to all wishlist users.

Table 15 — AUDIT_LOG
schema.sql L306–L320

No FKs intentionally — immutable log must survive record deletion. JSON columns for old_value/new_value. Written only by triggers, never by app.

Table 16 — NOTIFICATIONS
schema.sql L325–L342

Written by Triggers 13 (order status) + 14 (restock) and sp_broadcast_promo. Composite index (user_id, is_read) optimises unread count queries.

Table 17 — SHIPPING_ZONES
schema.sql L347–L360

Per-emirate rates. 7 UAE zones. Used by fn_zone_shipping_fee. Dubai: AED 10 std, AED 25 express, free >500. Fujairah: AED 25/45, free >1000.

Table 18 — TAGS
schema.sql L365–L373

Bestseller(amber), New Arrival(green), Limited(red), Eco Friendly(green), Staff Pick(blue), Clearance(gray), Bundle Deal(purple). color_hex for UI badges.

Table 19 — PRODUCT_TAGS
schema.sql L378–L388

1NF fix for M:N. Junction table resolves Products ↔ Tags. Composite PK (product_id, tag_id). Without this: tags="Bestseller,Staff Pick" in one column = 1NF violation.

Table 20 — ORDER_STATUS_HISTORY
schema.sql L393–L406

Full audit of every status transition. Written by Trigger 13 automatically. Order 1: pending→confirmed→processing→shipped→delivered with comments at each step.

Normalization — 1NF → BCNF

Functional Dependencies — Explicit Notation

-- USERS user_id → {email, password_hash, full_name, phone, role, is_active, last_login, created_at} email → {user_id} ← email is candidate key (UNIQUE constraint) -- CATEGORIES category_id → {name, parent_id, description, icon_url, is_active} name → {category_id} ← candidate key (UNIQUE) -- BRANDS brand_id → {name, country, website, logo_url} name → {brand_id} ← candidate key (UNIQUE) -- PRODUCTS product_id → {category_id, brand_id, name, slug, description, price, compare_price, stock_qty, sku, weight_kg, avg_rating, review_count, is_active, is_featured} slug → {product_id} ← candidate key (UNIQUE) sku → {product_id} ← candidate key (UNIQUE) -- ORDERS order_id → {user_id, address_id, coupon_id, subtotal, discount_amt, shipping_fee, tax_amt, total_amount, status, ordered_at} -- ORDER_ITEMS (composite PK) (order_id, product_id) → {quantity, unit_price} unit_price is NOT derived from product_id — it is the PRICE AT ORDER TIME (price snapshot) -- COUPONS coupon_id → {code, type, discount_value, min_order_amt, max_discount, expires_at, max_uses, used_count} code → {coupon_id} ← candidate key (UNIQUE) -- PRODUCT_ATTRIBUTES (composite PK) (product_id, attr_name) → {attr_value}
✅ First Normal Form (1NF)

Rule: All attributes atomic, no repeating groups.

Violations fixed:

  • Multiple images → PRODUCT_IMAGES table
  • Multiple tags → PRODUCT_TAGS junction
  • Variable specs → PRODUCT_ATTRIBUTES EAV
  • Multiple addresses → ADDRESSES table
✅ Second Normal Form (2NF)

Rule: In 1NF + no partial dependencies on composite keys.

Violation fixed: If street/city were in ORDERS: order_id, product_id → street — street depends on order, not product → partial dep. Fix: ADDRESSES table.

(order_id, product_id) → quantity ✓ fully depends on both

✅ Third Normal Form (3NF)

Rule: In 2NF + no transitive dependencies.

Violation fixed: product_id → brand_name → brand_country — brand_country depends on brand_name (non-key), not product_id directly. Fix: BRANDS table extracted.

Same issue with category_description → CATEGORIES extracted.

✅ BCNF

Rule: For every FD X→Y, X must be a superkey.

In PRODUCTS: determinants are product_id, slug, sku — all superkeys ✓

Without BRANDS: brand_name → country and brand_name is NOT a superkey of PRODUCTS → BCNF violation.

Views (7)

VIEW 1vw_product_catalogL415–L441
Complete product listing with brand, parent category, discount %, and primary image. Used by product grid API. 4-table JOIN stored as a view.
SELECT p.*, ROUND(((compare_price-price)/compare_price)*100) AS discount_pct,
  c.name AS category_name,
  pc.name AS parent_category,     -- self-join: c=Smartphones, pc=Electronics
  b.name AS brand_name,
  pi.url AS primary_image
FROM PRODUCTS p
JOIN  CATEGORIES c  ON p.category_id = c.category_id
LEFT JOIN CATEGORIES pc ON c.parent_id = pc.category_id   -- parent category
LEFT JOIN BRANDS b  ON p.brand_id = b.brand_id             -- NULL for books
LEFT JOIN PRODUCT_IMAGES pi ON pi.product_id=p.product_id AND pi.is_primary=1
VIEW 2vw_order_summaryL444–L471
Admin order dashboard — customer name, delivery address (CONCAT), item count (COUNT), payment status. GROUP BY order_id because of COUNT aggregate.
VIEW 3vw_revenue_by_categoryL474–L488
Revenue by category. Uses SUM(oi.quantity * oi.unit_price) with stored price snapshot — historically accurate. Excludes cancelled/refunded orders.
VIEW 4vw_low_stockL491–L504
Products with stock_qty ≤ 10 AND is_active=1, sorted by stock ASC. Mirrors the "Low stock" badge on ProductCard.tsx. Used by sp_dashboard_stats.
VIEW 5vw_customer_ltvL507–L523
Customer Lifetime Value. LEFT JOIN ORDERS includes customers with 0 orders. COALESCE handles NULL from empty LEFT JOIN. Only counts delivered (not cancelled/refunded) orders.
VIEW 6vw_product_tagsL1317–L1328
Products with all their tags as one string. Uses GROUP_CONCAT(t.name ORDER BY t.name SEPARATOR ', '). iPhone → "Bestseller, Staff Pick". Presentational only — data stays normalised in PRODUCT_TAGS.
VIEW 7vw_unread_notificationsL1331–L1342
Unread notification count per user. SUM(CASE WHEN is_read=0 THEN 1 ELSE 0 END) — counts only unread rows. LEFT JOIN keeps users with zero notifications.

Stored Functions (7)

Return a single value, callable in SELECT/WHERE. Either DETERMINISTIC or READS SQL DATA.

FUNCTION 1fn_apply_couponL532–L552
Calculates discount amount from a coupon. Handles percentage (with cap) and fixed types. Prevents discounting more than cart total.
IF type = 'percentage' THEN
  disc = ROUND(subtotal * val / 100, 2)
  IF max_discount IS NOT NULL AND disc > max_discount THEN disc = max_discount
ELSE disc = val  -- fixed amount
IF disc > subtotal THEN disc = subtotal  -- can't exceed cart value
RETURN disc

-- Example: fn_apply_coupon(2000,'percentage',50,800) → min(1000,800) = 800
FUNCTION 2fn_discounted_priceL555–L566
Generic % discount. ROUND(price*(1-pct/100),2). Handles NULLs, pct≤0 (return original), pct≥100 (return 0).
FUNCTION 3fn_cart_subtotalL569–L579
SUM(quantity × price) across CART_ITEMS JOIN PRODUCTS for a user. COALESCE(…,0) returns 0 for empty cart. Called by sp_place_order.
FUNCTION 4fn_validate_couponL583–L602
All-in-one coupon check: exists + is_active=1 + not expired + under max_uses + subtotal≥min_order_amt. Returns discount amount or 0.
FUNCTION 5fn_customer_order_countL605–L613
COUNT(*) of non-cancelled/refunded orders for a user. Used for loyalty tier logic.
FUNCTION 6fn_shipping_feeL616–L628
Weight-based shipping: ≤1kg→AED10, ≤5kg→AED20, ≤10kg→AED35, >10kg→AED50. Called by sp_place_order (×2 for Express).
FUNCTION 7afn_zone_shipping_feeL1351–L1365FUNCTION 7bfn_price_with_vatL1368–L1374
fn_zone_shipping_fee(emirate, is_express): looks up SHIPPING_ZONES, COALESCE fallback to 10/25.    fn_price_with_vat(price): ROUND(price*1.05,2) — UAE 5% VAT.

Triggers (14)

Auto-execute on INSERT/UPDATE/DELETE. Enforce rules at DB level — no app can bypass them.

TRIGGER 1BEFORE INSERTtrg_check_stock_before_orderL639–L651
On ORDER_ITEMS. Reads stock — if insufficient: SIGNAL SQLSTATE '45000' → aborts + ROLLBACK. BEFORE so we can stop the insert cleanly.
SELECT stock_qty INTO v_stock FROM PRODUCTS WHERE product_id = NEW.product_id;
IF v_stock < NEW.quantity THEN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Insufficient stock';
END IF
TRIGGER 2AFTER INSERTtrg_deduct_stock_after_orderL654–L659
On ORDER_ITEMS. Deducts stock: UPDATE PRODUCTS SET stock_qty = stock_qty - NEW.quantity. AFTER — Trigger 1 already confirmed stock is sufficient.
TRIGGER 3AFTER UPDATEtrg_restore_stock_on_cancelL663–L679
On ORDERS. Guard: NEW.status='cancelled' AND OLD.status NOT IN ('cancelled','refunded') — prevents double-restore. Multi-table UPDATE JOIN restores all products in one statement. Also writes AUDIT_LOG.
TRIGGERS 4/5/6AFTER INSERT/UPDATE/DELETEtrg_update_rating_on_*L682–L711
On REVIEWS. Auto-maintain PRODUCTS.avg_rating and review_count. Trigger 6 uses COALESCE(AVG,0) for when last review deleted (AVG of empty = NULL).
TRIGGER 7AFTER INSERTtrg_increment_coupon_usageL714–L721
On ORDERS. IF NEW.coupon_id IS NOT NULL: increments COUPONS.used_count. Enforces max_uses limit over time.
TRIGGER 8BEFORE INSERTtrg_auto_slug_on_insertL724–L731
On PRODUCTS. IF slug is empty: LOWER(REPLACE(name,' ','-')). BEFORE trigger can modify NEW.slug. "iPhone 15 Pro" → "iphone-15-pro".
TRIGGERS 9/10AFTER INSERT/UPDATEtrg_audit_product_insert / updateL734–L755
On PRODUCTS. Write JSON old/new values to AUDIT_LOG. Trigger 10 only fires IF OLD.price != NEW.price OR OLD.stock_qty != NEW.stock_qty — avoids noise.
TRIGGER 11BEFORE INSERTtrg_single_default_addressL758–L770
On ADDRESSES. If new row is is_default=1 and user already has a default: silently sets NEW.is_default=0. Can't UPDATE existing row in BEFORE trigger (MySQL restriction).
TRIGGER 12AFTER INSERTtrg_audit_user_registerL773–L779
On USERS. Logs every new registration to AUDIT_LOG with JSON_OBJECT('email', email, 'role', role).
TRIGGER 13AFTER UPDATEtrg_order_status_historyL1384–L1398
On ORDERS. Guard OLD.status <> NEW.status. Inserts into ORDER_STATUS_HISTORY AND sends customer notification — two INSERTs, one trigger, one transaction.
TRIGGER 14AFTER UPDATEtrg_notify_restockL1401–L1414
On PRODUCTS. Guard OLD.stock_qty=0 AND NEW.stock_qty>0. INSERT...SELECT from WISHLISTS — sends notification to every user who wishlisted the product in one set-based operation.

Stored Procedures (9)

PROCEDURE 1 ⭐sp_place_orderL791–L916
Full checkout in one transaction. Most complex object in the schema — 125 lines.
sp_place_order(user_id, address_id, coupon_code, pay_method, ship_method,
               OUT order_id, OUT message)

1.  Validate cart NOT empty
2.  Validate address belongs to user (security)
3.  Resolve coupon (check active+expiry+max_uses)
4.  fn_cart_subtotal() → subtotal
5.  Validate coupon min_order_amt
6.  fn_apply_coupon() → discount
7.  SUM(qty × weight_kg) → total weight
8.  fn_shipping_fee(weight) → shipping (×2 for Express)
9.  (subtotal - discount) × 0.05 → VAT
10. subtotal - discount + shipping + vat → total

START TRANSACTION
  INSERT INTO ORDERS
  CURSOR LOOP → INSERT ORDER_ITEMS (Triggers 1+2 fire per row)
  INSERT INTO PAYMENTS
  DELETE FROM CART_ITEMS (clear cart)
COMMIT

EXIT HANDLER FOR SQLEXCEPTION: ROLLBACK + order_id=-1 + RESIGNAL

10 KPI metrics in one SELECT row: total_customers, total_orders, total_revenue, active_products, pending_orders, low_stock_count, total_reviews, avg_order_value, items_in_carts, revenue_last_30d.
PROCEDURE 3sp_top_selling_products(limit)L936–L957
Top N by units_sold with revenue, brand, category. Excludes cancelled/refunded. CALL sp_top_selling_products(10).
PROCEDURE 4sp_user_order_history(user_id)L960–L990
Full order history — 7-table JOIN returning every column for a customer order page.
PROCEDURE 5sp_restock_productL993–L1010
Admin restock: reads old stock → UPDATE → AUDIT_LOG → return result. Note: if stock goes 0→>0, Trigger 14 fires automatically → notifies wishlist users.
PROCEDURE 6sp_monthly_revenue(year)L1013–L1026

Full-text + filtered search with pagination. Builds SQL dynamically via CONCAT. Uses MATCH(name,description) AGAINST(q IN BOOLEAN MODE). PREPARE/EXECUTE/DEALLOCATE for dynamic queries.

Complex Queries

All live in schema.sql L1276–L1534 as commented reference queries.

Q1 — Correlated Subquery

-- Products priced above their category average
SELECT p.name, p.price, c.name AS category,
  (SELECT ROUND(AVG(p2.price),2) FROM PRODUCTS p2 WHERE p2.category_id=p.category_id) AS cat_avg
FROM PRODUCTS p JOIN CATEGORIES c ON p.category_id=c.category_id
WHERE p.price > (
  SELECT AVG(p3.price) FROM PRODUCTS p3 WHERE p3.category_id = p.category_id  -- correlated!
)

The inner SELECT re-runs for each outer row using that row's category_id. In Smartphones (avg ~AED 4166): iPhone 15 Pro (4999) ✓, Samsung S24 Ultra (4499) ✓, OnePlus 12 (2999) ✗.

Q2 — Nested Subquery (3 levels)

SELECT u.full_name, SUM(o.total_amount) AS total_spent
FROM USERS u JOIN ORDERS o ON u.user_id=o.user_id WHERE o.status='delivered'
GROUP BY u.user_id
HAVING SUM(o.total_amount) > (
  SELECT AVG(s.tot) FROM (
    SELECT SUM(total_amount) AS tot FROM ORDERS WHERE status='delivered' GROUP BY user_id
  ) s
)

Q3 — Window Function RANK()

SELECT product_name, category_name, revenue,
  RANK() OVER (PARTITION BY category_name ORDER BY revenue DESC) AS cat_rank
FROM vw_revenue_by_category
-- RANK() ties get same number, skips next (1,1,3). DENSE_RANK() → 1,1,2. ROW_NUMBER() → 1,2,3

Q4 — EXISTS / NOT EXISTS

-- Buyers who never wrote a review (target for review-request emails)
SELECT u.user_id, u.full_name FROM USERS u
WHERE EXISTS     (SELECT 1 FROM ORDERS  o WHERE o.user_id=u.user_id)
  AND NOT EXISTS (SELECT 1 FROM REVIEWS r WHERE r.user_id=u.user_id)
-- EXISTS stops on first match (short-circuit). SELECT 1 — column doesn't matter.

Q5 — 5-Table JOIN

SELECT o.order_id, u.full_name, b.name AS brand, p.name AS product,
  oi.quantity, oi.unit_price, (oi.quantity*oi.unit_price) AS line_total
FROM ORDERS o JOIN USERS u ON o.user_id=u.user_id
JOIN ORDER_ITEMS oi ON o.order_id=oi.order_id
JOIN PRODUCTS p ON oi.product_id=p.product_id
LEFT JOIN BRANDS b ON p.brand_id=b.brand_id  -- LEFT: books have no brand

// addToCart — functional update to avoid stale closures
const addToCart = useCallback((product) => {
  setCartItems(prev => {
    const existing = prev.find(i => i.product.id === product.id);
    if (existing) return prev.map(i => i.product.id === product.id
      ? { ...i, quantity: i.quantity + 1 } : i);
    return [...prev, { product, quantity: 1 }];
  });
  showToast(`${product.name} added to cart`);
}, [showToast]);

Cheat Sheet — Professor Q&A

Click any question to expand the answer.

How many tables and what's the structure?
20 tables total. Core: USERS, PRODUCTS, ORDERS, ORDER_ITEMS, PAYMENTS. Supporting normalization: CATEGORIES (self-ref hierarchy), BRANDS (BCNF — extracted transitive dep), ADDRESSES (2NF — extracted from USERS). 1NF tables: PRODUCT_IMAGES, PRODUCT_ATTRIBUTES (EAV), PRODUCT_TAGS (M:N junction). Operational: CART_ITEMS, WISHLISTS, REVIEWS, COUPONS. System: AUDIT_LOG, NOTIFICATIONS, ORDER_STATUS_HISTORY, SHIPPING_ZONES, TAGS.
Why is BRANDS a separate table?
To achieve BCNF. Without it: product_id → brand_name → brand_country is a transitive dependency (brand_country depends on brand_name which is not a superkey of PRODUCTS). With BRANDS: brand_id → {name, country, website} and product_id → brand_id only. Every FD determinant is now a superkey.
Why does ORDER_ITEMS store unit_price?
Price snapshot. Product prices change over time. If we derived price from PRODUCTS.price, order history would show wrong amounts after price updates. Storing unit_price at order time preserves what the customer actually paid. Also removes the transitive dependency item_id → product_id → current_price which would violate 3NF.
What happens if stock runs out mid-order?
Trigger 1 (trg_check_stock_before_order) fires BEFORE each INSERT into ORDER_ITEMS. If stock_qty < requested quantity, it raises SIGNAL SQLSTATE '45000' (user-defined exception). The EXIT HANDLER in sp_place_order catches this → ROLLBACK (undoes all inserts so far) → sets order_id=-1 → RESIGNAL to API caller → API returns error to frontend.
What does the CURSOR in sp_place_order do?
A cursor iterates over a result set row-by-row inside procedural SQL. Here it reads each cart item (product_id, quantity, price) and inserts it into ORDER_ITEMS one at a time. This is necessary because Trigger 1 (stock check) fires per INSERT — we need row-by-row processing. Pattern: DECLARE CURSOR FOR SELECT... → OPEN → LOOP: FETCH INTO vars → INSERT → END LOOP → CLOSE.
How does avg_rating stay accurate automatically?
Three AFTER triggers on REVIEWS: Trigger 4 (INSERT), 5 (UPDATE), 6 (DELETE) — each recalculates and writes back to PRODUCTS: UPDATE PRODUCTS SET avg_rating = (SELECT AVG(rating) FROM REVIEWS WHERE product_id = NEW.product_id). Trigger 6 uses COALESCE(AVG,0) because AVG of empty set = NULL. This is intentional denormalisation for performance — no JOIN needed on every page load.
Why does AUDIT_LOG have no foreign keys?
An audit log must be permanent and immutable. If AUDIT_LOG.record_id had a FK to PRODUCTS, deleting a product would either (a) cascade-delete its audit trail (destroying evidence) or (b) block deletion (management problem). No FKs makes it append-only. It records history that must survive regardless of what happens to the source records.
What is SIGNAL SQLSTATE '45000'?
MySQL's mechanism to raise a user-defined exception from a trigger or procedure. SQLSTATE '45000' = unhandled user-defined exception. It aborts the current statement, propagates up through the call stack, and if inside a transaction triggers a ROLLBACK unless caught by a DECLARE EXIT HANDLER FOR SQLEXCEPTION. The message text is user-readable: "Insufficient stock for this product".
Explain the EAV pattern in PRODUCT_ATTRIBUTES
Entity-Attribute-Value: one row per attribute per product. (product_id=1, attr_name='RAM', attr_value='8GB'). Used because different product categories have completely different specs — a smartphone needs RAM/Storage/OS, a tennis racket needs string_tension/grip_size/shaft_flex. Adding 50+ nullable columns to PRODUCTS for all possible specs would waste space and be unmanageable. EAV trades query simplicity for flexibility.
How does the frontend work without a backend server?
Next.js output:"export" generates fully static HTML+CSS+JS files. All data fetching is client-side via fetch() in useEffect hooks. The Railway backend is optional — if unreachable, the catch block silently keeps MOCK_PRODUCTS (8 hardcoded products in data/products.ts). The "Live · Railway DB" / "Offline · Mock data" badge in the corner shows which source is active.
What is the self-referencing FK in CATEGORIES?
parent_id is a FK pointing back to category_id in the same CATEGORIES table. NULL = top-level. Electronics (id=1, parent=NULL) → Smartphones (id=6, parent=1). Enables unlimited hierarchy depth. ON DELETE SET NULL means if a parent is deleted, children become top-level (parent_id=NULL) rather than being deleted or orphaned.
What are the 7 coupon codes and how do they work?
WELCOME10 (10%, any order, max AED500), SUMMER20 (20%, min AED200, max AED800), FLASH50 (50%, min AED1000, max AED2000), VIP30 (30%, min AED500, max AED1500), STUDENT15 (15%, min AED100, max AED300), FLAT100 (AED100 off, min AED500), TECH500 (AED500 off, min AED5000). fn_validate_coupon checks all conditions. fn_apply_coupon calculates discount. Trigger 7 auto-increments used_count per order.
Why is email VARCHAR(191) not VARCHAR(255)?
MySQL InnoDB with utf8mb4 charset has a 767-byte index limit per column. utf8mb4 uses up to 4 bytes per character. 255 × 4 = 1020 bytes which exceeds the limit. 191 × 4 = 764 bytes — just under 767. So VARCHAR(191) is the maximum length for a utf8mb4 column to have a regular index (UNIQUE). This is a well-known MySQL constraint.
Difference between RANK(), DENSE_RANK(), ROW_NUMBER()?
All are window functions with OVER (PARTITION BY ... ORDER BY ...). For scores [100, 100, 90]: RANK() → 1,1,3 (skips 2 after tie). DENSE_RANK() → 1,1,2 (no gap). ROW_NUMBER() → 1,2,3 (unique, arbitrary for ties). We use RANK() in Q3 to rank products by revenue within each category — two products with equal revenue get the same rank.
What is the difference between BEFORE and AFTER triggers?
BEFORE triggers fire before the operation and can modify NEW.column values (useful for auto-generating slugs, enforcing defaults, blocking inserts via SIGNAL). AFTER triggers fire after the operation succeeds and can't modify the row that was just changed — used for cascading actions like updating related tables, writing to AUDIT_LOG, or sending notifications. You can't UPDATE the same table in a BEFORE trigger (MySQL restriction — prevents recursion).
